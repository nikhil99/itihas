# Itihas — Indian history timelines

A static website for exploring Indian history as interactive timelines.
Names, places and empires are clickable everywhere, with summaries, images,
coordinates and Marathi names pulled from Wikipedia and Wikidata.

Timelines so far: **The Maratha Empire** series, an overview plus eight detailed timelines:
Shivaji, Sambhaji, Rajaram & Tarabai, Shahu, Bajirao I, Nanasaheb, Madhavrao I,
Nana Phadnavis & Mahadji Shinde, and Bajirao II.

## Run it

`site/data/` is generated and not committed, so build it once after cloning
(the first run fetches from Wikipedia and takes a while; later runs use `.cache/`):

```bash
python3 scripts/build_data.py
python3 scripts/serve.py
```

Then open http://localhost:8095

## How it works

```
content/                 <- what you edit (curated, hand-written)
  entities/<topic>.json  people / places / polities / concepts -> Wikipedia title,
                         split by topic (maratha, mughal, british, …); the build merges them
  timelines/<id>.json    one file per timeline: lanes, context bars, events
scripts/build_data.py    fetches Wikipedia + Wikidata, validates, writes site/data/
site/                    the website (plain HTML/CSS/JS, no build step)
  data/                  generated by build_data.py; not committed
```

After editing anything in `content/`, rebuild:

```bash
python3 scripts/build_data.py
```

API responses are cached in `.cache/`. Pass `--refresh` to re-fetch.
The script exits non-zero and lists problems (unknown ids, wrong Wikipedia
titles, places with no coordinates) so mistakes surface right away.

### Adding an event

```json
{
  "id": "sinhagad", "date": "1670-02-04", "lane": "military", "major": true,
  "title": "Battle of Sinhagad",
  "summary": "Tanaji Malusare scales the cliffs of Kondhana…",
  "people": ["tanaji", "shivaji"], "places": ["sinhagad"],
  "polities": ["mughal-empire"], "wiki": "Battle of Sinhagad"
}
```

- `date` can be `YYYY`, `YYYY-MM` or `YYYY-MM-DD`. Add `"end"` for a span and `"approx": true` for "c." dates.
- Names in `summary` that match a referenced entity's title or `aliases` turn into links automatically.

### Timeline-level fields

| field | meaning |
|---|---|
| `subject` | entity whose portrait and summary head the page |
| `kind` | `empire` puts it in the Empires row and the river; `state` titles its series "— the great houses"; `party` titles its series by the series name alone |
| `series`, `order` | groups timelines on the home page and drives the ← → links (`order: 0` = the series overview) |
| `region` | defaults to `India`; any other value (e.g. `Japan`) gets its own home-page section and stays out of the Indian river, "On this day" and series lists |
| `range` | initial visible years |
| `focus` | `[from, to]` years to shade (defaults to the subject's lifespan) |
| `intro` | optional text replacing the Wikipedia summary in the header |
| `aliases` | old ids of timelines merged into or renamed to this one; links to them redirect here |
| `guide` | optional "Start here" panel for newcomers: `chapters` (title, from, to, text, why, `image` entity, key `events`), `compare` (`before`, `after`, `rows` of [label, before, after]), `cast` (entity + one-line role) and `chain` (cause → effect steps, each optionally linked to an `event`). Picking a chapter moves the timeline to its years. See `meiji-restoration.json` |
| `territories` | optional map layer for the map's Play button: `geo` names a file in `content/geo/` (GeoJSON features with ids), and each of `areas` (`id`, `from`, optional `to`, `label`, `note`, `event`, `style: "protectorate"`) fades in and out on its dates. `scripts/make_geo_japan.py` shows how `japan-empire.json` was cut from Natural Earth |
| `context` | bars in the "People & powers" section; `from`/`to` override Wikidata dates (e.g. reigns) |

Event-level `"see": "<timeline-id>"` adds an "Open the full timeline →" link to that card.
`"major": true` puts the event on the always-visible **Key events** track.

### Adding a timeline

Copy `content/timelines/shivaji.json` and register any new people or places in
`content/entities/` — use a new `<topic>.json` file for a new topic. Entity ids must be
unique across all files (the build checks this). It shows up on the home page after a rebuild.

### Family trees

Any timeline with a `rulers` row whose rulers are mostly related gets a family tree under
its timeline. The build reads father, mother, child and spouse links from Wikidata for
registered people, and `content/families.json` corrects them: name-only connectors
(`people`), wrong links (`remove`), missing or adopted links (`add`), heirs who never
ruled (`heirs`) and short card notes (`notes`).

## Sources and licence

Summaries and images come from Wikipedia (CC BY-SA) and Wikidata (CC0). The event selection
and short event descriptions are curated here. Where dates are contested
(Shivaji's birth year, the Rohideshwar oath), the event text says so.

## Books

Visual guides to books live in `site/books/` as standalone pages (plain HTML/CSS/JS, the same
palette and fonts as the site) and are listed in `site/books/books.json`. That manifest feeds the
**Books** row on the home page and `#/books`. Its `timelines` field links each book to related
timelines. To add a book, drop `site/books/<id>.html` next to the others and add an entry to
the manifest. Nothing needs rebuilding.

**Data-driven guides.** Most guides are a JSON file plus a one-line page: `site/books/<id>.json` holds
the hero (`title`, `byline`, `lede`, `facts`, `related`, `note`) and a list of `sections`, and
`<id>.html` is just `<body data-guide="<id>">` with `book.css`, `book.js` and `guide.js`. `guide.js`
draws each section by its `type` (`timeline`, `steps`, `compare`, `table`, `cards`, `bars`, `chips`,
`list`, `quote`), and a section's `ch` (plus optional `pages`) adds its link back to the chapter.

**References to the source.** Each manifest entry lists its `chapters` (`n`, `title`, and a `url` for
books that are online or `pages` for printed ones), plus `source` (the whole book online) and
`edition`. `book.js` uses them in two ways. It turns `<a class="ref" data-ch="2" data-pages="52–53"></a>`
into a link to chapter 2 (or its page range), and it adds a "Read the book" chapter list before the
footer of every book page. Put a `ref` under each section of a guide so a reader can go from any
claim to the chapter it came from.

**Citing a book on a timeline.** An event can cite chapters with
`"sources": [{"book": "<book id>", "chapter": 6, "pages": "52–53"}]` (`pages` is optional). The build
checks the book id and chapter number against `books.json`, and the event card shows
"Source: *Book title*, ch. 6 · read ↗". Use this for any timeline entry added or corrected
because of a book.

## Parampara

Guru–shishya lineages live in `site/parampara/` and are listed in `site/parampara/parampara.json`,
which feeds the **Parampara** row on the home page and `#/parampara` (same fields as a book card,
with `guru` and `span` in place of author and date). Each lineage is two files: a data file
`<id>.json` and a small page `<id>.html` (copy `ramakrishna.html` and change `data-lineage`).
`lineage.js` draws the tree from the data file, so a new lineage needs no new code.

The data file has `title`, `intro`, `note`, related `timelines`, and a `tree` of people:
`{ "name", "alt", "dates", "kind", "role", "note", "tl", "children" }`. `kind` is `guru`, `monastic`,
`householder`, `woman`, `western` or `influence` (influence draws a dashed line: influenced, not
initiated). `tl` links a person to their Itihas timeline. `{ "group": "…", "children": [...] }`
gathers siblings under a foldable label. `open` lists the branches that start unfolded and `select`
the person shown first. An optional `succession` (`title`, `intro`, `list` of `name`, `years`, `note`)
draws a numbered list of heads of the order below the tree. A lineage can add or relabel kinds with
`kinds` (`label`, `color`, `dashed`, `via`, `plural`) and reword the line legend with `lines`;
`varkari.json` uses this for companions and later saints who had their own gurus. Nothing needs rebuilding.

## Map playback

Every timeline's map has a **Play** button and a year slider. Playback runs through the years: places appear when their first event happens, pulse as events occur, and major events are captioned under the map. Timelines with `territories` also show borders changing over time (the Meiji timeline shows the Japanese empire growing).

## Compare view

`#/compare/<id>,<id>,…` puts up to five timelines on one axis (picker at `#/compare`, or the
"Compare with other timelines" button on any timeline). Each timeline keeps its own colour: its
rulers (or, for a person, their lifetime) become ruler rows, its events one event row, and the
years where they coincide are shaded and listed as overlaps. Built in `buildCompare()` in
`site/app.js` by merging the timelines into one synthetic timeline, so all the normal timeline,
story, map and panel code is reused.

Live at **https://itihas.vokalglobe.com**. Every push to `main` deploys `site/` to GitHub Pages
(`.github/workflows/pages.yml`). Rebuild `site/data/` with `scripts/build_data.py` and commit it

## Working on several things at once

Several Claude chats (or you and a chat) can work in parallel without stepping on each other:

1. **One worktree per chat.** Each piece of work gets its own folder and branch:
   ```bash
   git worktree add ../Itihas-<topic> -b <branch> origin/main
   cp -R .cache ../Itihas-<topic>/    # optional: reuse cached Wikipedia responses
   ```
   Never switch branches in a folder another chat is using.
2. **Merge through pull requests.** CI builds and validates every PR; `main` deploys on merge.
3. **Content only in branches.** `site/data/` is generated in CI, and entities live in topic
   files, so two branches adding different timelines don't conflict. After merging, pull
   and rebuild locally: `python3 scripts/build_data.py`.
4. Clean up a finished worktree with `git worktree remove ../Itihas-<topic>`.
